راهنمای راه‌اندازی Zeus Cloud Deployer خصوصی
==============================================

نکته مهم:
این نسخه دیگر Tokenهای Cloudflare را در IndexedDB یا LocalStorage مرورگر نگهداری نمی‌کند.
حساب‌ها در D1 ذخیره و Tokenها با AES-256-GCM در سمت سرور رمزگذاری می‌شوند.
برای همین قبل از ورود باید D1 و Secrets را متصل کنید.

۱) ساختار GitHub
----------------
محتویات این بسته را داخل پوشه cloudflare-deployer در مخزن فعلی قرار دهید و فایل‌های قدیمی همان پوشه را جایگزین کنید.
ساختار نهایی داخل پوشه cloudflare-deployer باید این باشد:

cloudflare-deployer/
  public/index.html
  public/app.js
  public/_headers
  functions/_lib/shared.js
  functions/api/auth/login.js
  functions/api/auth/me.js
  functions/api/auth/logout.js
  functions/api/auth/password.js
  functions/api/accounts.js
  functions/api/accounts/[id].js
  functions/api/users.js
  functions/api/users/[id].js
  functions/api/token/verify.js
  functions/api/deploy.js
  functions/api/health.js
  src/deployer-core.js
  src/worker-d1-migration.js
  migrations/0001_init.sql

در تنظیمات Build پروژه Pages:
- Root directory: cloudflare-deployer
- Build command: exit 0
- Build output directory: public
- Production branch: main

۲) ساخت D1
------------
در داشبورد Cloudflare:
Workers & Pages → D1 SQL Database → Create database
نام پیشنهادی: zeus-deployer-db

بعد از ساخت دیتابیس، وارد Console همان D1 شوید و تمام محتوای فایل زیر را اجرا کنید:
migrations/0001_init.sql

این مرحله جدول‌های کاربران، نشست‌ها، حساب‌های Cloudflare و مجوز دسترسی را ایجاد می‌کند.

۳) اتصال D1 به Pages
--------------------
Workers & Pages → انتخاب پروژه cloudflare-deployer → Settings → Bindings
Add binding → D1 database
Variable name را دقیقاً DB قرار دهید.
دیتابیس zeus-deployer-db را انتخاب و Save کنید.
برای اعمال Binding، یک بار پروژه را Redeploy کنید.

۴) افزودن Secrets و Variables
-----------------------------
در پروژه Pages:
Settings → Variables and Secrets → Production → Add

این مقادیر را اضافه کنید:

BOOTSTRAP_ADMIN_USERNAME
Value: ali
Type: Secret یا Variable

BOOTSTRAP_ADMIN_PASSWORD
Value: رمز اولیه مدیری که در گفت‌وگو تعیین کردید
Type: Secret

VAULT_ENCRYPTION_KEY
Value: یک کلید تصادفی Base64 معادل ۳۲ بایت
Type: Secret

برای تولید کلید VAULT_ENCRYPTION_KEY روی رایانه دارای OpenSSL اجرا کنید:
openssl rand -base64 32

خروجی را کامل کپی و به‌عنوان Secret با نام VAULT_ENCRYPTION_KEY وارد کنید.
این کلید را گم نکنید و در GitHub قرار ندهید. اگر این کلید عوض شود، Tokenهای ذخیره‌شده قبلی دیگر قابل رمزگشایی نخواهند بود.

پس از Save کردن متغیرها و Secrets، Pages را Redeploy کنید.

۵) اولین ورود مدیر
------------------
صفحه سایت را باز کنید و با مشخصات بوت‌استرپ وارد شوید:
Username: ali
Password: همان رمز اولیه‌ای که برای BOOTSTRAP_ADMIN_PASSWORD تنظیم کردید.

اولین ورود موفق، حساب مدیر را با هش PBKDF2 و salt تصادفی در D1 ایجاد می‌کند.
پس از اولین ورود:
- از دکمه «تغییر رمز» یک رمز قوی حداقل ۱۲ نویسه‌ای انتخاب کنید.
- سپس BOOTSTRAP_ADMIN_USERNAME و BOOTSTRAP_ADMIN_PASSWORD را از Variables and Secrets حذف کنید.
- حذف این دو متغیر مانع ورود عادی نمی‌شود؛ حساب مدیر از قبل در D1 ثبت شده است.
- پس از حذف متغیرها یک Redeploy انجام دهید.

نکته مهم درباره خطای PBKDF failed:
Cloudflare Workers سقف ۱۰۰٬۰۰۰ تکرار برای PBKDF2 دارد. نسخه قبلی مقدار ۳۱۰٬۰۰۰ داشت و به همین دلیل ساخت اولین حساب مدیر در محیط واقعی Cloudflare با خطای PBKDF failed متوقف می‌شد. در این نسخه مقدار به ۱۰۰٬۰۰۰ اصلاح شده است. چون جدول users در دیتابیس شما خالی است، نیازی به پاک‌کردن یا تغییر داده‌های کاربران نیست. اگر در آینده هش رمزهایی با مقدار بیشتر از ۱۰۰٬۰۰۰ از محیط دیگری وارد کنید، این Worker قادر به اعتبارسنجی آن‌ها نخواهد بود؛ رمز را از مسیر بازیابی/بازنشانی داخل همین Worker دوباره هش کنید. برای جبران محدودیت هزینه هش، از رمز عبور بلند و یکتا (ترجیحاً ۱۶ نویسه یا بیشتر)، محدودیت تلاش ورود و کنترل دسترسی استفاده کنید.

۶) افزودن حساب Cloudflare
-------------------------
با حساب مدیر وارد شوید.
در «مدیریت حساب‌های Cloudflare» نام حساب، Account ID و API Token را وارد کنید.
دکمه ساخت خودکار توکن فرم رسمی Cloudflare را با نام و مجوزهای پیشنهادی از قبل پر می‌کند و اگر Account ID معتبر وارد شده باشد، دامنه مجوز را به همان حساب محدود می‌کند؛ ایجاد نهایی و کپی Token باید توسط خود شما انجام شود. Zone در این قالب روی همه Zoneها قرار دارد، چون مجوز Workers Routes برای قابلیت‌های دامنه استفاده می‌شود.
سپس Token را در فرم وارد و «ثبت حساب جدید» را بزنید.
تا ۱۰ حساب قابل ثبت است. Token رمزگذاری شده و هیچ‌وقت از API به مرورگر بازگردانده نمی‌شود.

۷) ایجاد کاربر و دادن دسترسی
----------------------------
در «مدیریت کاربران و سطح دسترسی» نام کاربری و رمز اولیه (حداقل ۱۲ نویسه) را بسازید.
حساب‌هایی را که آن شخص مجاز است استفاده کند تیک بزنید و «ایجاد کاربر» را انتخاب کنید.
کاربر فقط همان حساب‌ها را می‌بیند و فقط با همان حساب‌ها می‌تواند Deploy و Health Check انجام دهد. زیر هر حساب، گزینه جداگانه «اجازه Clean Rebuild» وجود دارد؛ این اجازه به‌صورت پیش‌فرض خاموش است تا کاربر نتواند Worker را حذف و بازسازی کند، مگر آنکه مدیر صریحاً اجازه بدهد.
مدیر می‌تواند دسترسی‌ها را تغییر دهد، کاربر را غیرفعال یا حذف کند و رمز او را بازنشانی کند.

۸) استفاده از Deploy
--------------------
- حساب مجاز را انتخاب کنید.
- سورس پیش‌فرض Clean IPs از قبل قرار دارد:
  https://raw.githubusercontent.com/babaeali626-dot/clean-ips/refs/heads/main/worker%2Cjs
- نام Worker را وارد کنید.
- در صورت نیاز D1 و KV را فعال کنید.
- Obfuscator و Clean Rebuild همچنان در دسترس‌اند.
- Deploy را بزنید.

هشدار: Clean Rebuild Worker قبلی را حذف می‌کند؛ تنظیمات یا Secretهای قبلی Worker را پیش از حذف پشتیبان بگیرید.

۹) محدودیت پایش
----------------
پایش فعلی در مرورگر انجام می‌شود و فقط تا وقتی صفحه باز باشد ادامه دارد.
برای پایش ۲۴ ساعته مستقل از مرورگر باید بعداً Cron Worker جداگانه متصل شود.

۱۰) الزامات امنیتی
------------------
- رمزهای مدیر و VAULT_ENCRYPTION_KEY را در GitHub commit نکنید.
- پس از اولین ورود، رمز اولیه را عوض کنید و Secrets بوت‌استرپ را حذف کنید.
- برای هر حساب Cloudflare از Token با کمترین مجوز موردنیاز استفاده کنید.
- دسترسی افراد دیگر را فقط به حساب‌های موردنیاز محدود کنید.
- از D1 و VAULT_ENCRYPTION_KEY پشتیبان امن نگهداری کنید.
- این پنل از Cookie نشست HttpOnly/Secure/SameSite=Lax، هش PBKDF2 و رمزگذاری AES-GCM استفاده می‌کند؛ با این حال مدیریت Secretهای Cloudflare و کنترل دسترسی حساب اصلی همچنان بر عهده مدیر است.


۱۱) بررسی Token و Migration D1
-------------------------------
- دکمه «تست زنده API Token» از مسیر GET /accounts/{account_id}/tokens/verify در Cloudflare استفاده می‌کند و فعال بودن Token را بررسی می‌کند.
- سپس APIهای فهرست Workers و D1 را Probe می‌کند تا قابلیت مشاهده سرویس‌ها تأیید شود. پاسخ Verify سطح دقیق Edit را برنمی‌گرداند؛ مجوز نوشتن با عملیات واقعی Deploy، ساخت D1 و اجرای query تأیید می‌شود.
- API استقرار نام Worker را پیش از شروع stream با الگوی ^[a-z0-9_-]{1,63}$ بررسی می‌کند؛ هسته Deploy و Health نیز همین اعتبارسنجی را انجام می‌دهند.
- اگر سوییچ D1 روشن باشد، D1 پیدا یا ساخته می‌شود، سپس سه دستور پایه از src/worker-d1-migration.js جداگانه و به شکل idempotent اجرا می‌شوند و Binding (به‌صورت پیش‌فرض DB) در Metadata Multipart Worker قرار می‌گیرد.
- این Migration فقط جدول‌های عمومی zeus_app_metadata و zeus_schema_migrations را ایجاد می‌کند؛ جدول‌های اختصاصی اپلیکیشن Worker باید با Migration ویژه همان سورس اضافه شوند.
- همه درخواست‌های Cloudflare دارای Timeout هستند و خطای شبکه، Timeout، مجوز و اعتبارسنجی با پیام مشخص برگردانده می‌شود.

توجه مجوز: برای ساخت یا حذف Worker جدید ممکن است Workers Admin در سطح Product لازم باشد؛ Editor برای Workerهای موجود است.


۱۲) تفاوت مجوز Editor و Admin در Cloudflare
-------------------------------------------
فرم Token به‌صورت خودکار مجوزهای استاندارد Workers Scripts Edit، D1 Edit، KV Edit و Workers Routes Edit را انتخاب می‌کند. طبق مدل نقش‌های جدید Cloudflare، Workers Editor برای Deploy/به‌روزرسانی Worker موجود کافی است؛ اما ساخت یا حذف Worker جدید به Workers Admin در سطح Product نیاز دارد. بنابراین اگر Worker با نام جدید می‌سازید یا Clean Rebuild انجام می‌دهید و HTTP 403 می‌گیرید، دسترسی Product-level Admin را در پنل Cloudflare بررسی کنید. فرم Template قدیمی به‌تنهایی نمی‌تواند این تفاوت نقش جدید را تضمین کند.

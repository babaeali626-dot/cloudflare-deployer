راهنمای ساخت و استقرار Cron Worker برای Zeus Cloud Deployer v3.3

این نسخه از پنل، تنظیمات پایش و بازسازی خودکار را در D1 ذخیره می‌کند؛ اما پایش داخلی آن به باز بودن تب مرورگر وابسته است. پوشه cron-worker یک Worker زمان‌بندی‌شده جداگانه اضافه می‌کند تا پایش حتی با بسته بودن پنل ادامه داشته باشد.

مهم: Cron به D1 اصلی خود پنل متصل می‌شود؛ نه D1هایی که برای Workerهای نصب‌شده توسط پنل ساخته می‌شوند. نام Binding دیتابیس در Cron باید دقیقاً DB باشد و VAULT_ENCRYPTION_KEY باید عیناً همان Secret فعلی Pages باشد.

مرحله ۱ ـ فایل‌های پروژه
- فایل ZIP نسخه v3.3-Cron را استخراج کنید.
- پوشه cloudflare-deployer را در همان مخزن GitHub و همان مسیر قبلی جایگزین کنید.
- تنظیمات Cloudflare Pages را تغییر ندهید. اگر قبلاً همین ساختار را داشتید:
  Root Directory: cloudflare-deployer
  Build command: exit 0
  Build output directory: public
- D1 فعلی پنل و Secret با نام VAULT_ENCRYPTION_KEY را حذف یا عوض نکنید.

مرحله ۲ ـ پیدا کردن D1 اصلی پنل
- وارد Cloudflare Dashboard شوید.
- از بخش Workers & Pages، قسمت D1 SQL Databases را باز کنید.
- دیتابیسی را پیدا کنید که در Cloudflare Pages به‌عنوان Binding با نام DB وصل شده است.
- نام دقیق Database و Database ID آن را یادداشت کنید.
- از D1 مربوط به Workerهای نصب‌شده توسط پنل استفاده نکنید؛ Cron باید همان دیتابیس کاربران، نشست‌ها و حساب‌های ذخیره‌شده پنل را ببیند.

مرحله ۳ ـ تنظیم فایل Wrangler
فایل cloudflare-deployer/cron-worker/wrangler.toml را باز کنید و دو مقدار زیر را با اطلاعات D1 اصلی پنل جایگزین کنید:
  database_name = "نام دقیق D1 پنل"
  database_id = "شناسه D1 پنل"

binding را تغییر ندهید و دقیقاً DB باقی بگذارید.

مرحله ۴ ـ استقرار Cron Worker
- روی کامپیوتر، داخل پوشه cloudflare-deployer ترمینال باز کنید.
- Wrangler را وارد حساب Cloudflare کنید و Cron را مستقر کنید:

  npx wrangler login
  npx wrangler deploy --config cron-worker/wrangler.toml

- سپس Secret رمزگشایی Tokenها را برای همین Cron Worker نیز تنظیم کنید:

  npx wrangler secret put VAULT_ENCRYPTION_KEY --config cron-worker/wrangler.toml

- هنگام درخواست مقدار Secret، همان مقدار فعلی VAULT_ENCRYPTION_KEY در تنظیمات Pages را وارد کنید. این مقدار را برای کسی ارسال نکنید و در GitHub قرار ندهید.

مرحله ۵ ـ بررسی فعال بودن Cron
- در Cloudflare Dashboard به Workers & Pages بروید.
- Worker با نام zeus-deployer-cron-monitor را باز کنید.
- Settings یا Triggers را باز کنید.
- باید Cron Trigger زیر را ببینید:
  */5 * * * *
- در بخش Logs، لاگ‌های اجرای scheduled را بررسی کنید.

نحوه عملکرد
- Cron هر ۵ دقیقه بیدار می‌شود.
- فاصله واقعی بررسی هر حساب از مقدار Monitor Interval ذخیره‌شده برای همان حساب خوانده می‌شود؛ مقدار پیش‌فرض v3.3 برابر ۱۰ دقیقه است.
- فقط حساب‌هایی بررسی می‌شوند که حداقل یک بار با موفقیت Deploy شده‌اند و Health Check آن‌ها روشن است.
- پس از اولین خطای واقعی Health Check، در صورت روشن بودن Auto Rebuild و وجود مجوز Clean Rebuild، بازسازی اجرا می‌شود؛ آستانه قدیمی ۳ نادیده گرفته می‌شود.
- بین دو تلاش بازسازی حداقل یک ساعت فاصله گذاشته می‌شود.
- خطاهای API، توکن نامعتبر، خطای دسترسی یا خطای رمزگشایی به‌عنوان خرابی Worker شمرده نمی‌شوند و به‌تنهایی باعث Rebuild نخواهند شد.
- بررسی سلامت، Deploy عادی و Clean Rebuild از قفل مشترک استفاده می‌کنند تا هم‌زمان روی یک حساب اجرا نشوند.
- نتیجه آخرین اجرای Cron در D1 ذخیره می‌شود و با باز کردن دوباره حساب، در گزارش پایش پنل نمایش داده می‌شود.

نکات مهم
- Cron Worker را Pages به‌صورت خودکار Deploy نمی‌کند؛ فقط یک بار جداگانه با Wrangler مستقرش کنید.
- نام D1 و شناسه آن باید مربوط به دیتابیس اصلی پنل باشد.
- Secret را عیناً از Pages کپی کنید، ولی آن را در فایل wrangler.toml یا مخزن Git قرار ندهید.
- اگر مجوز Clean Rebuild برای حساب وجود نداشته باشد، Cron فقط سلامت را بررسی می‌کند و بازسازی را رد می‌کند.
- Cron برای هر بار اجرا حداکثر ۵۰ حساب را می‌خواند. برای تعداد بیشتر از ۵۰ حساب، باید محدودیت/صف پردازش افزایش داده شود.


به‌روزرسانی One-Failure
- از اولین نتیجه ناموفق واقعی Health Check، Clean Rebuild شروع می‌شود. Worker قبلی با API حذف و سپس سورس ذخیره‌شده دوباره نصب می‌شود.
- مقدار قدیمی failureThreshold=3 در تنظیمات D1 نادیده گرفته می‌شود و مقدار مؤثر دقیقاً ۱ است؛ زمان بازسازی قدیمی نیز در اولین اجرای نسخه جدید یک‌بار پاک می‌شود تا اولین خطا معطل cooldown قبلی نماند.
- برای جلوگیری از چرخه حذف/نصب، بین تلاش‌های بازسازی حداقل یک ساعت فاصله وجود دارد. پس از یک Health Check سالم، این محدودیت برای خرابی بعدی از نو محاسبه می‌شود.
- خطاهای API، احراز هویت، مجوز یا رمزگشایی Token نامشخص‌اند و هرگز به‌تنهایی باعث حذف Worker نمی‌شوند.
- بعد از جایگزینی فایل‌ها در GitHub، Pages از مسیر معمول به‌روزرسانی می‌شود و Cron Worker نیز باید دوباره مستقر شود: `npx wrangler deploy --config cron-worker/wrangler.toml`. نیازی به تغییر D1 یا Secret قبلی نیست.

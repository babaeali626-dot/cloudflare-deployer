راهنمای به‌روزرسانی Zeus Cloud Deployer v3.3

۱) جایگزینی فایل‌ها در GitHub
- فایل ZIP نسخه v3.3 را استخراج کنید.
- محتوای پوشه cloudflare-deployer را در همان مسیر قبلی مخزن GitHub جایگزین کنید.
- شاخه production قبلی را نگه دارید.
- تنظیمات Cloudflare Pages را تغییر ندهید:
  Root Directory: cloudflare-deployer
  Build command: exit 0
  Build output directory: public

۲) Binding و کلید رمزگذاری
- همان D1 فعلی پنل را با نام Binding دقیق DB نگه دارید.
- VAULT_ENCRYPTION_KEY را تغییر ندهید؛ Token حساب‌های ذخیره‌شده با همین کلید رمزگشایی می‌شوند.
- جدول account_deploy_settings در اولین انتخاب حساب به‌صورت خودکار ساخته می‌شود. اجرای دستی migrations/0002_account_deploy_settings.sql اختیاری است.
- دیتابیس D1 پنل را حذف نکنید.

۳) نام‌های تصادفی و ذخیره بر اساس حساب
- با انتخاب هر حساب Cloudflare، اگر برای آن حساب پروفایل قبلی وجود نداشته باشد، نام Worker، D1 و KV به‌صورت تصادفی ساخته و در D1 پنل ذخیره می‌شود.
- دکمه «نام تصادفی» کنار Worker و دکمه «رندم» کنار D1 و KV نام جدید می‌سازند.
- تغییر نام‌ها و تنظیمات با ذخیره خودکار انجام می‌شود.
- پروفایل‌ها به شناسه رکورد حساب در پنل متصل‌اند؛ با انتخاب حساب دیگر، نام‌ها و تنظیمات همان حساب بارگذاری می‌شوند. این اطلاعات در D1 خود پنل ذخیره می‌شوند، نه در LocalStorage مرورگر.
- نام‌ها از حروف کوچک انگلیسی، عدد، خط تیره و زیرخط ساخته می‌شوند.

۴) لینک نهایی پنل
- خروجی استقرار لینک مستقیم پنل را می‌دهد و مسیر آن همیشه به /panel ختم می‌شود.
- اگر سورس Worker مسیر محرمانه‌ای قبل از panel دارد، در فیلد «مسیر پنل» آن را وارد کنید؛ نمونه:
  qna61nmQZUnG/panel
- اگر فقط qna61nmQZUnG را وارد کنید، برنامه /panel را اضافه می‌کند.
- اگر فقط panel وارد کنید، آدرس خروجی به شکل https://WORKER.ACCOUNT.workers.dev/panel خواهد بود.
- اگر Worker مسیر محرمانه دیگری دارد، مسیر را از تنظیمات همان Worker بردارید؛ برنامه مسیر تصادفی داخل سورس را حدس نمی‌زند.

۵) استقرار و بررسی خودکار
- «بررسی سلامت خودکار پس از استقرار» به‌صورت پیش‌فرض روشن است.
- «استقرار / بازسازی خودکار در صورت خرابی» نیز به‌صورت پیش‌فرض روشن است.
- پس از Deploy موفق، پایش سلامت به‌صورت خودکار شروع می‌شود.
- با انتخاب دوباره حسابی که قبلاً Worker آن Deploy شده، پایش در صورت روشن بودن گزینه بررسی دوباره شروع می‌شود.
- مقدار پیش‌فرض فاصله بررسی ۱۰ دقیقه و آستانه ۳ شکست واقعی متوالی است.
- پس از رسیدن به آستانه، Clean Rebuild خودکار اجرا می‌شود؛ بین دو بازسازی حداقل یک ساعت فاصله اعمال می‌شود.
- خطاهای خود API پایش به‌عنوان خرابی Worker شمرده نمی‌شوند و به‌تنهایی باعث حذف Worker نمی‌شوند.
- این پایش در مرورگر انجام می‌شود؛ برای ادامه کار پس از بسته‌شدن صفحه یا مرورگر، Cron Worker مستقل لازم است.
- کاربر عادی باید از طرف مدیر برای همان حساب اجازه Clean Rebuild داشته باشد؛ در غیر این صورت API عملیات بازسازی را با 403 رد می‌کند.

۶) توصیه ایمنی
- Clean Rebuild Worker قبلی را حذف می‌کند. پیش از استفاده، از تنظیمات و Secretهای Worker پشتیبان بگیرید.
- D1 اصلی پنل و VAULT_ENCRYPTION_KEY را حذف یا تغییر ندهید.
- استقرار اولیه همچنان با فشردن دکمه Deploy توسط کاربر انجام می‌شود؛ گزینه خودکار برای پایش و بازسازی پس از خرابی است، نه Deploy خودکار و بی‌اجازه هنگام ورود به حساب.
